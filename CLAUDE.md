# BinDay — project instructions

Waste collection schedule PWA for Žalgirio g. 8A, Juragiai. Live at
https://gerimantas.github.io/BinDay/, installable to a phone home screen.

**The app serves this one address only** (user decision, 2026-10-18). The address picker,
saved addresses, geolocation, settings sheet and the background download of `dist/` were
removed from the app. `dist/` and the bulk pipeline stay in the repo, unused by the app.

**Use the `binday` skill** (`.claude/skills/binday/` in this repo) for anything touching the
schedule data or the operator sites. It holds the resolved container ids, the fast PDF path
for Švara, the Power BI driving for Ekonovus, and the traps each site sets. Don't re-derive
the scraping path by hand — it is non-obvious and the skill was hardened through a 6-agent
eval that found 8 real defects.

## Architecture

Single HTML file **as served**. No framework, no dependencies, no backend, and no build
step for the user — the app must work offline at the kerb. `index.html` carries markup,
styles, the schedule data and the ICS export in one file.

**Edit `src/`, never `index.html`.** The root `index.html` is generated by concatenating
`src/` and is overwritten on every build. The sources are plain scripts sharing one scope —
no `import`/`export`, no bundler — so the output is the same kind of file the browser
already ran.

```bash
python tools/build_app.py            # rebuild index.html, bump sw.js CACHE
python tools/build_app.py --check    # verify index.html matches src/ (writes nothing)
```

`tools/build_app.py` bumps `CACHE` automatically, so the most common deploy mistake is no
longer something to remember. It only bumps when the output actually changed.

| File | Purpose |
|------|---------|
| `src/index.html` | Markup shell with `<!--STYLES-->` / `<!--SCRIPTS-->` markers |
| `src/styles.css` | All CSS |
| `src/js/*.js` | One file per concern; `tools/build_app.py` `ORDER` is the load order |
| `index.html` | **Generated** — the deployed artefact. Do not edit |
| `tools/build_app.py` | Assembles `src/` → `index.html`, bumps `CACHE` |
| `tools/atomic.py`, `tools/atomic.mjs` | Atomic writes + `.meta.json` sidecars for fetch |
| `sw.js` | Service worker, cache-first |
| `manifest.json` | PWA manifest |
| `qr.html`, `qr.png` | Scan sheet linking to the live app |
| `data/raw/` | Fetch output. Written, never deleted. Gitignored |
| `dist/` | **Committed** — all Kauno r. addresses. Built by `build_dist.py`, gated by `check_dist.py`. The app does not read it |
| `tools/update_zalgirio_schedule.py` | Monthly update: rewrites `DEFAULT_SCHEDULE` and the check dates in `src/js/data.js` |
| `data/zalgirio_svara.json` | Švara dates for this address, refreshed by hand (see Turnstile below) |
| `data/Atlieku_isvezimo_grafikai.md` | Legacy. Nothing reads it |
| `.evals/` | Eval scenarios for the `binday` skill — run them after editing it |

The schedule lives in `src/js/data.js` as `DEFAULT_SCHEDULE`, read through `getSchedule()`.
Never mutate it in place. `update_zalgirio_schedule.py` rewrites `DEFAULT_SCHEDULE`,
`DEFAULT_COLLECTED` and the `DEFAULT_CHECKED_*` lines by regex — keep those names and their
one-line form, or the monthly update fails (or, for `DEFAULT_COLLECTED`, silently stops).

## Rules that break things when ignored

**Bump `CACHE` in `sw.js` on every deploy that changes `index.html`.** The worker is
cache-first, so installed clients keep serving the old schedule forever otherwise.
`build_app.py` does it; read the current value in `sw.js`. This is the single most common way
a correct fix fails to reach the phone.

**Store published dates, never `anchor + intervalDays`.** Švara's schedule genuinely
deviates — the window before 2026-08 contained Monday pickups and an off-cycle Wednesday run
on 2026-07-22, confirmed on the site. A computing app silently skips those, and a missed
pickup is the one failure the user actually notices. Same reason the ICS writes one `VEVENT`
per day instead of an `RRULE`.

**Never extrapolate past a container's `until` date.** It is the operator's published
horizon, not a guess. Past it the app says "refresh needed" rather than inventing dates.
Coverage differs per operator — Švara publishes a rolling window, Ekonovus a fixed forward
count — so one container expiring before the others is normal.

**Use `isoLocal()`, never `toISOString()`.** The latter converts to UTC and rolls the date
back an hour before midnight in Lithuania, making the app claim a pickup is "today" on the
evening before.

**Write files as UTF-8 explicitly.** Windows defaults to cp1252 and Lithuanian diacritics
crash the write.

**Keep `apple-touch-icon.png`.** iOS ignores the manifest icons when adding to the home
screen and substitutes a screenshot of the page without it.

## Calendar export — known client limits

Found the hard way; all three are undocumented:

- **Google keeps only the first `VALARM`** from an imported ICS. The file correctly carries
  reminders at 17:00 and 20:00 the evening before; Google drops the second. Fix is a
  dedicated Google calendar with two default notifications, not a change to the file.
  Worse in practice: on the 2026-10-18 phone re-import **none** of the 38 events kept
  either alarm — all use the calendar's default reminder. (One July event, 2026-08-04, did
  keep both; the reason is unknown.) Repair after each import: Google Calendar MCP
  `update_event` on every upcoming event with `useDefaultReminders: false` and popup overrides
  420 and 240 min (= 17:00 and 20:00 the evening before), `notificationLevel: NONE`. The event
  id is `_` + lowercase base32hex of the UID, no padding. Done for all 38 on 2026-10-18.
- **Google ignores `COLOR:`.** The colour coding is carried by an emoji in the summary
  instead, chosen to match the app's neon palette.
- **`RRULE` cannot express off-cycle dates**, which is why every pickup is its own event.

Event UIDs are stable per date (`binday-YYYYMMDD@binday.local`, unchanged since the first
release). Google derives its event id from the UID — `_c9kmsp31…` is base32hex of
`binday-20261027@binday.local` — so a re-import targets the same events, not new copies.
Confirmed 2026-10-18: re-import from the phone updated 24 events, added 14, no duplicates.
On Android the button only saves the file to Downloads; the import happens when the user
opens `binday.ics` from the download notification or Files and picks the calendar app.

**The app cannot see the calendar.** It records only that the file was downloaded, and the
button says exactly that. The 2026-07-31 import was made from the phone with the app's
button and was still the only one on 2026-10-18, ending 2027-07-20. Updating needs another
press of the button each time new dates arrive — nothing is automatic.

## The data pipeline

```
data/raw/   fetch writes here, never deletes    (gitignored; tools/fetch_*)
dist/       build owns it, safe to wipe          (committed; tools/build_dist.py)
```

If `dist/` is destroyed it rebuilds from `raw/` in seconds with no network. If `raw/` is
destroyed the operators must be asked again — about an hour. That asymmetry is why only
fetch may write `raw/`, and why `build_index.py`, which deleted files it had not created,
is gone.

```bash
python tools/precheck.py                  # 0 unchanged, 10 changed, 1 could-not-tell
node tools/fetch_svara.js                 # Kauno r. only; --all or --regions "A,B"
python tools/fetch_ekonovus.py            # code 52 only; --codes all to widen
node tools/fetch_dates_svara.mjs          # 2 concurrent by default; ~9 min at --concurrency 8
python tools/fetch_dates_ekonovus_bulk.py # ~1.5 min, four requests for the area
python tools/build_dist.py                # raw/ -> dist/
python tools/check_dist.py --previous <d> # publish gate; must pass before committing
```

**Bulk refresh is deliberately not automated.** `health.yml` checks only Žalgirio g. 8A
monthly (two Ekonovus containers live, the Švara one from a file) and validates the committed
`dist/`. If that address gains newer dates it raises a warning for manual review; it does
not enumerate municipalities, catalogues, or every container schedule. Run the bulk tools
above only when the user explicitly requests a wider rebuild.

**Švara is behind Cloudflare Turnstile since 2026-10.** Every request without a session
cookie gets HTTP 403 `Užklausa neleidžiama.` — API, PDF and ICS alike, from a runner or a
home IP. The cookie (`__Host-gs_session`, 30 min) is issued by `POST /api/session` only after
"Verify you are human" passes, so a GitHub runner cannot read Švara and we do not automate
past it. Its Žalgirio dates live in `data/zalgirio_svara.json`, refreshed in a watched
browser with `tools/svara_session_dates.js` (Claude in Chrome: open
`https://grafikai.svara.lt/`, then `javascript_tool` with the file's text on that tab; the
user's own Chrome passed without a checkbox on 2026-10-12); the monthly run fails with "Švara needs a manual check" when the file is over
92 days old or its dates end within 90 days. The bulk Švara tools are broken by the same gate.

**`precheck.py` is monitoring-only.** The scheduled GitHub workflow instead runs
`tools/update_zalgirio_schedule.py`, which fetches and publishes only the three resolved
Žalgirio g. 8A containers. Exit 10 from the precheck means the Ekonovus dates
changed; exit 1 means the operator could not be checked. Neither result starts a bulk
refresh.

**The app fetches nothing.** The dates ship inside `index.html`; a new schedule reaches the
phone as a new build through the service worker's update offer. Operators were never fetched
live: Švara sends no `Access-Control-Allow-Origin` (verified on its PDF and ICS endpoints), its
address chain is seroval-encoded behind `/_serverFn/`, and Ekonovus lives in a Power BI
embed needing a real browser. Schedules change about once a year, so nothing needs to be
fetched live — a backend proxy was prototyped, proven to work, and rejected for that
reason.

## Both operators serve valid-looking wrong answers

Ekonovus serves a **valid-looking wrong answer** when a slicer fails to apply — a complete
schedule for an unrelated container in another municipality, with no error.

**Švara does the same by a different mechanism: every `getcontracts` field is a `Contains`
match, not equality.** `houseNumber=5` returns `15-1`, `35`, `15C` and `3-5` (the last
because the *flat* contains a 5). Asking for `Žalgirio g. 8A` without a locality also returns
`Žalgirio g. 28A` in another village. Send all five fields (`region`, `subDistrict`, `city`,
`address`, `houseNumber`) and **always read the returned `fullAddress` back** before trusting
dates. With all five present it is exact (103/103 probes). `getschedule` is safe — a wrong or
neighbouring `wasteObjectId` returns empty, never another container's dates.

## The address key is (locality, street, house, flat) — all four

Measured against fetched dates, not match rates. Dropping **locality** gives another
village's schedule: of 1 442 street+house keys present in several localities, 1 406 (97.5%)
have different dates. Dropping the **flat** gives the neighbour's schedule: every multi-flat
building assigns each flat its own container, and 60% of Švara multi-flat buildings have
different dates per flat.

Earlier notes said the opposite for both ("merge on street+house, locality is a display
label"; "a container stands at a building, not a flat"). Those are superseded and marked as
such in `DECISIONS.md`. An overlap percentage cannot distinguish a merged duplicate from a
wrong schedule — verify key changes against dates.
